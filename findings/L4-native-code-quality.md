# L4 — Native Code Quality (Braze-Senior Lens)

## Verdict

- **0.1.0 ready:** PASS with caveats (no BLOCKERs found; the SDK Authentication-bypass and iOS custom-attribute dispatch issues are MAJOR but consumer-recoverable through documentation + workarounds).
- **Braze-senior review:** GAP. The code is clean and convention-following — far above the average community bridge — but four findings would draw written comments from a Braze SDK engineer: (1) `changeUser` does not enforce that `sdkAuthSignature` is present when SDK Authentication was opted-in at init, (2) iOS `setCustomUserAttribute` dispatch order silently truncates non-integer doubles, (3) Capacitor 6/7 forward-compat is claimed but the peer dep pins `^6.0.0` only, (4) iOS BrazeUI is linked but never wired so IAM doesn't render out of the box. Several MINOR items round out the picture; none individually fail the lens but the SDK-auth one in particular is on `REVIEW_READINESS.md` §3's explicit "forbidden" list.

## Summary

Across 731 lines of Swift, 940 lines of Kotlin, 1048 lines of TS definitions, and 770 lines of web impl, the code is **disciplined**: no `!!`, no Swift force-unwraps, no `Any`-types in TS, no `@Suppress`, no `TODO` or `FIXME`, no reflection, no private API. C01 method anatomy holds — 35 `@objc func` ↔ 35 `CAP_PLUGIN_METHOD` ↔ 35 `@PluginMethod` with name parity verified by diff. Init guards via shared helpers per platform (`requireInitialized`, `requireUser`). Error messages follow the C01 format consistently. PII never appears in any log or error path.

The findings concentrate in three areas a senior reviewer cares about most: **security defaults enforced end-to-end (SDK Authentication)**, **threading + lifecycle on iOS BrazeKit 14.x** (post-API-reshape), and **wire-format faithfulness** for custom attributes when numbers cross the JS/native boundary. Each is fixable in well under a day; together they're the distance between "good community plugin" and "Braze-endorsable".

## What's good

- **C01 method anatomy holds across all 35 methods.** `diff` of @objc Swift methods, CAP_PLUGIN_METHOD registrations, and @PluginMethod Kotlin functions yields zero divergence (verified with literal sort + diff). Method-name parity is rare on multi-platform bridges; this one nails it.
- **Zero `!!` force-unwraps in Kotlin (`android/src/main/java/com/bma342/braze/BrazePlugin.kt`).** Verified by grep. Every nullable goes through `isNullOrEmpty()` checks or `requireUser`/`requireInitialized` helpers.
- **Zero Swift force-unwraps (`ios/Plugin/BrazePlugin.swift`).** All exclamation marks are negations (`!apiKey.isEmpty`) or boolean negations (`&& !allowInsecure`). Confirmed by `grep -nP '(\w)!(?!=)'` returning empty.
- **`[weak self]` discipline (`ios/Plugin/BrazePlugin.swift:121, 127`).** Both subscription closures capture self weakly with proper guard-let unwrap. Retain-cycle-free.
- **PII never appears in any log or error path.** Every error message names a field, never a value. The closest case (`android:326` interpolating `value?.javaClass?.simpleName`) leaks only the Java class name, not the value. C06 §3 compliance verified.
- **HTTPS enforcement matches C06 §2 with strict equality.** Both `ios/Plugin/BrazePlugin.swift:95-100` and `android/.../BrazePlugin.kt:127-134` use the strict pattern with the same error message text referencing SECURITY.md §4. `src/web.ts:756-763` does the same. Cross-platform discipline holds.
- **Init guards consistently applied via shared helpers.** iOS `Self.requireInitialized(call)` (line 724-730), Android `requireInitialized(call)` (line 772-778) + `requireUser(call)` (line 786-797), Web `this.requireInitialized()` (line 454-459) + `this.requireUser()` (line 468-478). Every post-init method uses the helper — no ad-hoc null checks.
- **`@CapacitorPlugin` (Android) + `@objc(BrazePlugin)` (iOS) + `CAP_PLUGIN(BrazePlugin, "Braze", ...)` (Obj-C).** All three registration mechanisms align under the plugin name "Braze". No drift.
- **`PrivacyInfo.xcprivacy` ships in podspec resource_bundles (`CapacitorBraze.podspec:17-19`), declares no tracking, no required-reason API access** — accurate for the plugin layer (BrazeKit ships its own manifest aggregating into the consumer app). Apple's submission rules don't get the plugin maintainer in trouble; the consumer-app maintainer still owns ATT.
- **`consumer-rules.pro` ships and is wired via `consumerProguardFiles` (`android/build.gradle:36`).** Means consumer apps with R8 minification won't strip plugin methods. The rules are slightly broader than needed (see L4-K05 critique below) but they cover the surface.
- **Exact pins on native SDKs.** `BrazeKit '14.1.0'`, `BrazeUI '14.1.0'`, `com.braze:android-sdk-ui:42.2.0`. Per C08, exact-pin policy is non-negotiable; all three pins match. The web peer-dep range `^6.0.0` is per the intentional asymmetry C08 documents.
- **Native bridge wire format goes through SDK-canonical encoders.** `flag.json()` (iOS, `ios:482-491`), `flag.forJsonPut()` (Android, `android:620-626`). When BrazeKit / Braze Android SDK ship wire-format changes, the bridge follows automatically rather than maintaining a parallel encoder. This is exactly the right pattern.
- **Init-independent privacy/lifecycle methods deliberately bypass the init guard.** `ios/Plugin/BrazePlugin.swift:660-708` and `android/.../BrazePlugin.kt:722-752`. Both explicitly comment the asymmetry with C07 (iOS BrazeKit 14.x lost the class-level `enableSDK`/`isDisabled` so `enableSDK` and `isDisabled` on iOS require init). The deviation is *documented at the code site* — exactly the discipline a senior reviewer wants to see.

## What would specifically annoy a Braze senior

Mapping to `REVIEW_READINESS.md` §3's "10 things that annoy" list, one by one:

1. **Re-implementing Braze functionality.** No evidence. Every method calls the matching SDK entry point. Custom logic is limited to (a) hex decoding the APNs token because `@capacitor/push-notifications` emits hex, (b) discriminating content-card subtypes on web because the SDK doesn't expose a tag field, (c) gender enum mapping to keep the public string-based contract stable. All three are bridge translation, not reimplementation. ✓
2. **Vendoring Braze SDK code.** No. Pinned via CocoaPods + Maven Central + npm peer. ✓
3. **Logging or echoing PII.** Verified clean. The only place a runtime value touches a string is the Java class-name interpolation in Android's `setCustomUserAttribute` error path (L4-K03), which leaks a type name, not a value. ✓
4. **Weakening security defaults vs native SDK.** `enableLogging` defaults to false (matches Braze SDK), `allowInsecureEndpoint` defaults to false (stricter than Braze SDK — Braze SDK accepts http URLs without protest). HTTPS enforcement is duplicated on the bridge per C04. ✓
5. **Bridge that violates threading assumptions.** Mostly clean. iOS subscription closures fire on whatever queue BrazeKit dispatches them on; `notifyListeners` is Capacitor-thread-safe. Android `IEventSubscriber` callbacks fire on Braze's internal executor; `notifyListeners` handles dispatch. No `runBlocking` or main-thread blocking. One MAJOR concern at L4-S03 — the re-entrance lifecycle on iOS could fire callbacks from a stale subscription during init-twice. Otherwise clean.
6. **Breaking ProGuard / R8 minification.** `consumer-rules.pro` is shipped and wired (L4-K05 nits the breadth, not the presence). ✓
7. **Missing `PrivacyInfo.xcprivacy` on iOS.** Shipped via podspec resource_bundles (L4-S11 nits the empty BrazeUI link, not the manifest). ✓
8. **Forking README copy from Braze docs.** Outside this audit's scope.
9. **Implying official Braze endorsement.** `package.json:4` says "Unofficial, community-maintained ... Not affiliated with or endorsed by Braze, Inc." ✓
10. **Abandoned-looking repo.** Outside this audit's scope.

**The one item that would draw a written comment in a Braze-senior PR review:** Item #4's subitem about SDK Authentication. Findings L4-K01, L4-S01, L4-T01 together describe a real "weakening security defaults" pattern — when a consumer opts into `enableSdkAuthentication: true`, the plugin should enforce that `changeUser` calls carry a signature, not silently accept signature-less calls. This is on the explicit "what would annoy" list as item #5. It's a one-day fix; without it, the plugin advertises SDK Auth support but doesn't enforce it.

**The second item that would draw a written comment:** L4-S02 — iOS custom-attribute dispatch order silently truncates fractional doubles. A senior reviewer testing `setCustomUserAttribute({ key: 'avg_order', value: 42.5 })` on both platforms would see Android log 42.5 and iOS log 42, and the question "why?" would consume the review.

**The third:** L4-S11 — BrazeUI linked but not used. A senior reviewer would either expect IAM to render out of the box (it won't on iOS) or expect the dependency to not be there. The middle ground is the worst outcome.

Severities recap: 6 MAJORs (3 on the SDK-auth gap across platforms, 1 on iOS dispatch order, 1 on iOS re-entrance, 1 on Capacitor peer-dep range, 1 on Kotlin Long truncation, 1 on iOS BrazeUI unused), 25 MINORs/NITs. No BLOCKERs.
